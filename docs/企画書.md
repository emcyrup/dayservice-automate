# そだちノート ─ 放課後デイサービス業務AI（企画書 / ドラフト v0.1）

> 放課後等デイサービス事業所向けに、**日々の記録・保護者連絡・計画作成・加算チェック**をAIで自動化するSaaS。
> 「書類のための残業」をなくし、スタッフを子どもと向き合う時間に戻す。

作成日: 2026-07-22 / ステータス: 企画ドラフト

---

## 1. 背景と課題

放課後等デイサービスの現場では、支援そのものより**書類業務の負担**が離職・人手不足の大きな要因になっている。

| 現場の痛み | 具体的な状況 |
|---|---|
| 毎日の記録が重い | 児童ごとの活動記録を手書き／PC入力。閉所後の残業で対応 |
| 保護者への報告が手間 | 連絡帳・アプリで一人ひとりに文章を作成 |
| 個別支援計画の作成 | 6ヶ月ごとの作成・見直しが義務。児発管に集中し高負荷 |
| 加算申請書類の不備 | 算定要件を満たす根拠記録の抜けが、実地指導で返還リスクに |
| スタッフの離職 | 書類残業が離職の一因。採用難で悪循環 |

**重要な特殊性**: 放デイの記録は単なるメモではなく、**報酬請求・加算算定・実地指導（監査）に直結する法定書類**である。ここが介護・保育の一般的な記録ツールとの差別化ポイントになる。

---

## 2. 提供価値（バリュープロポジション）

> **「話すだけで、記録も報告も計画も下書きが終わる。加算の取りこぼしと書類不備をAIが見張る。」**

- **時短**: 記録・報告文作成の時間を大幅削減 → 残業削減 → 離職防止
- **増収／損失防止**: 加算の算定漏れ防止・減算アラートで、事業所の収益を守る
- **品質の底上げ**: 経験の浅いスタッフでも、AIの下書きで一定水準の記録・報告が書ける

「時短ツール」ではなく **「お金（加算）と監査リスクを守るツール」** として訴求する。

---

## 3. ターゲットとビジネスモデル

- **対象**: 他事業所への展開（自社利用ではなくSaaS提供）
- **初期ターゲット**: 1〜3拠点程度の中小規模の放デイ事業所（IT専任がいない現場）
- **課金モデル**: 月額サブスクリプション
  - 事業所単位の基本料金 + 児童数 or スタッフ数に応じた従量、の2軸を想定
  - 例: 基本 ¥XX,XXX/月 + 児童1人あたり ¥XXX/月（数値は要検証）
- **導入ハードル低減**: ビルド不要・スマホですぐ使える設計。初期設定を最小に。

---

## 4. 機能（MVP と ロードマップ）

### フェーズ1 — MVP（本プロトタイプの範囲）
1. **音声で活動記録** … スマホで話す → AIが活動記録フォーマットに自動整形
2. **保護者への報告文を自動生成** … 記録から保護者向けのトーンでリライト（送信前に人がレビュー）

### フェーズ2
3. **個別支援計画の下書き生成** … アセスメント＋活動記録から長期/短期目標・支援内容の草案を作成（児発管が仕上げる）
4. **加算チェック** … 記録・計画・配置を突き合わせ、算定要件の根拠記録の有無を判定・アラート

### フェーズ3（将来）
- 連絡帳アプリ/LINE連携、モニタリング記録、実地指導向けの書類一括出力、経営ダッシュボード（稼働率・加算算定状況）

> 優先度の考え方: **毎日発生する①②を最速で価値化 → 収益直結の④で乗り換え不可の存在に**。

---

## 5. 差別化ポイント

- **放デイ制度に特化**: 個別支援計画の周期、加算要件、減算リスクを前提にした設計（汎用記録ツールにはない）
- **音声ファースト**: 福祉職はPCよりスマホ。「話すだけ」でリテラシー不問
- **人が最終責任を持つUX**: AIは下書き・チェックに徹し、送信/確定は必ず人が行う → 誤情報とコンプラの両面をケア
- **更新可能な加算ルール**: 報酬改定に追従できるよう、要件をハードコードせずデータ/ルールとして保持

---

## 6. 技術構成（シンプル志向）

プロトタイプは **ビルド不要の静的Webアプリ（単一HTMLファイル）** で構成。

```
[スマホ/PCブラウザ]
   ├─ 音声認識: Web Speech API（ブラウザ標準、追加コストなし）
   ├─ UI: HTML/CSS/JS（フレームワークなし・スマホファースト）
   ├─ データ: localStorage（プロト）→ 本番はDB
   └─ AI生成: デモ用の内蔵ジェネレータ
             └─ 本番は Claude API（記録整形/報告/計画下書き）に差し替え
```

本番移行時の想定（いずれもシンプル構成を維持）:
- フロント: そのままのWeb（PWA化でアプリ風に）
- バックエンド: 軽量API（記録・児童・計画・加算要件の保存 / AI呼び出しの中継）
- AI: Claude API。記録整形・報告生成・計画下書きはLLM、加算チェックは「ルール＋LLM判断」のハイブリッド
- データ: 児童マスタ／活動記録／計画／加算要件をリレーショナルに。**編集履歴を保持**（監査対応）

---

## 7. セキュリティ・コンプライアンス（最重要）

児童の氏名・障害情報は最高レベルの**要配慮個人情報**。信頼が導入の前提条件になる。

- 国内リージョン・通信/保存の暗号化
- AIに顧客データを学習させない（API利用のオプトアウト前提）
- アクセス権限管理・操作 log（誰がいつ編集したか）
- AI生成物は**必ず人がレビュー・承認してから確定/送信**するフロー
- 加算要件は制度改定で変わる前提 → 更新可能な形で保持

---

## 8. 展開ステップ

1. **MVP検証**: 本プロトタイプで①②の体験を協力事業所に見せ、業務フィット・時短効果をヒアリング
2. **パイロット導入**: 1〜2事業所で実データ運用。加算チェック（④）の要件精度を詰める
3. **正式提供**: 料金確定・セキュリティ体制整備・サポート導線を用意しSaaS展開

### 検証したいKPI（例）
- 記録1件あたりの作成時間（Before/After）
- 保護者報告の作成時間・送信までのリードタイム
- 加算算定漏れ・減算アラートの検知件数
- スタッフの残業時間

---

## 9. リスクと対応

| リスク | 対応 |
|---|---|
| 個人情報漏えい | 暗号化・権限管理・学習オプトアウト・国内リージョン |
| AIの誤生成がそのまま流れる | 人のレビュー承認を必須化するUX |
| 制度改定で加算要件が変わる | 要件をデータ/ルール化し更新可能に |
| 現場が使いこなせない | 音声ファースト・ボタン最小の徹底したシンプルUI |
| 音声認識の精度（専門用語） | 児童名・活動は選択式にし、話すのは所感のみ→精度向上 |
