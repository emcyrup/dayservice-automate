# そだちノート → みちのーと 移行計画

そだちノート(放課後等デイサービス・`index.html`)を、個別支援計画ワークベンチ「みちのーと」(添付プロトタイプ / `emcyrup/michinote`)をベースにした別プロジェクトへ移します。**デザインと画面の骨格はみちのーと、機能はそだちノートのものをそのまま持ち込む**のが方針です。

作成日: 2026-09-03

---

## 1. 両者の現状

| | そだちノート(移行元) | みちのーと(移行先ベース) |
|---|---|---|
| 構成 | 単一HTML(CSS/JS内包・約1,750行) | ES modules(`src/app.js` 2,280行・`plan-engine.js`・`record-workflow.js`・`demo-data.js`)+ 本番SaaS(`saas.html`・`server/`・PostgreSQL) |
| 保存 | `localStorage` に1つのDB(`children[]` + 各記録に `childId`) | ローカルデモは `localStorage`(`michi-note-demo-v1`、**利用児ごとに別の状態**を切り替え)。SaaSは PostgreSQL + RLS |

## 3. 先に決めていただきたいこと

### A. どの層に載せるか(最重要)

| 案 | 内容 | 向き |
|---|---|---|
| **A-1 ローカルデモ層**(`index.html` + `src/`、localStorage) | そだちノートと同じ「端末内保存・サーバ不要」で、まず機能を全部そろえる | 検証・デモを続けながら進める場合。**推奨(第1段階)** |
| A-2 本番SaaS層(`saas.html` + `server/` + PostgreSQL) | 実績・請求・加算チェックをテーブル設計・RLS・権限・監査ログまで含めて実装 | 本番化を直接目指す場合。設計量が大きい(第2段階として扱うのが現実的) |

推奨は **A-1 → A-2 の2段階**です。A-1で機能とデータ形を確定してから、A-2で同じデータ形をテーブルに落とすと手戻りが少なくなります。

### B. データの持ち方

みちのーとのデモは「利用児ごとに別の状態」を切り替える構造ですが、実績・請求は**全児童を横断して月次集計**するため、そだちノートと同じ「1つのDBに `students[]` と `studentId` 付きの記録」へ寄せる必要があります。
→ 新しいスキーマ(例: `michi-note-v2`)を定義し、`michi-note-demo-v1` と そだちノートのバックアップJSON(`exportData`)の両方から取り込める移行関数を用意します。

### C. AIの扱い

みちのーとは「日誌からの下書きは決定論的。根拠不足は自動決定しない」が設計思想です。そだちノートのClaude生成は、この思想を壊さないよう **「🤖 AI下書き(任意・必ず人が確認)」** として併存させます。サーバ側の文章補助(`writing-assist.js`、現在はOpenAI)とClaudeリレーは、プロバイダを切り替えられる1つのサービスにまとめる案です(どちらのキーもサーバ環境変数のみ・フロントに出さない)。

### D. 名前

プロダクト名は「みちのーと」に統一し、そだちノートは「旧名」として検証ガイドにだけ残す想定です。別名にする場合はお知らせください。

## 5. 移行しない/後回しにするもの

- そだちノートのデザインスキン(2026-09-03に当てた「みちのーと風」CSS) ― 移行先は本家のCSSなので不要。CareOne側のスキンはそのまま残す

- みちのーとSaaSの Cognito / AWS 構成 ― A-1では触らない
