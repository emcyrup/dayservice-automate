# AI基盤の構成方針 — 「LMを構築する」の正しい形(Claude + RAG)

「加算などの様式に対応するために、LMを構築して、過去事例や情報をもとに帳票作成や申請を行えるようにしたい」という要件に対する技術方針です。

作成日: 2026-08-21 / 対象: 両プロダクト(先行実装は かけはしノート 📑申請アシスタント)

---

## 1. 結論: 専用LMは「学習」せず、Claude + RAG(検索拡張生成)で構成する

「過去事例をもとに帳票を作るAI」を実現する方法は2つあります。

| 方式 | 仕組み | 判定 |
|---|---|---|
| ① 専用LMの学習(ファインチューニング) | 過去事例を教師データにしてモデル自体を訓練する | ❌ 採用しない |
| ② **Claude + RAG(検索拡張生成)** | 事例を**データベースに貯め、生成のたびに検索してAIのプロンプトに渡す** | ✅ **採用** |

### 専用LM学習を採用しない理由

1. **制度改定に追随できない** — 学習済みモデルに焼き込んだ知識は、報酬改定のたびに再学習(データ整備→訓練→評価→配備)が必要。介護・障害福祉は3年ごとの大改定+随時のQ&A発出があり、追随コストが現実的でない。RAGなら**事例・制度情報を入れ替えるだけ**。
2. **データ量が足りない** — 1事業所の届出・帳票は年に数十件程度。ファインチューニングに必要な量・多様性に遠く及ばず、過学習した「それらしいが間違う」モデルになる。
3. **コストと運用負担** — 学習基盤・GPU・MLエンジニアが必要になり、SaaSの価格に転嫁できない。RAGはDB+検索+API呼び出しのみ。
4. **根拠を示せない** — 学習済みモデルの出力は「なぜその文になったか」を遡れない。RAGは**参照した事例をそのまま画面に提示**でき、行政に出す書類として説明責任を果たせる(申請アシスタントの「② 参照した過去事例」)。
5. **個人情報を学習に使わない方針と整合** — 顧客データをモデルに焼き込まない(学習オプトアウト)という本プロダクトのセキュリティ方針は、RAGなら構造的に守られる(データはDBに留まり、生成のたびに一時的に渡すだけ)。

## 2. 構成(検証版 → 本番)

```
[事例ライブラリ]                [生成]
 過去の届出文例                  作成対象(例: 特定事業所加算 届出一式)
 記載例・手引きの要点     →      ① アプリ内の体制データを自動で流し込み
 社内の記載ルール                ② 関連事例を類似検索(top-k)
      │                          ③ ①+②をClaudeのプロンプトに構成
      └── 追加した瞬間から       ④ 下書き生成 → 人が確認・修正 → 提出
          次の生成に反映
```

| 層 | 検証版(現在) | 本番 |
|---|---|---|
| 事例の保存 | localStorage(端末内)＋**任意で事業所共有(リレーサーバ経由のFirestore同期。2026-08-22実装)** | サーバDB(法人単位の共有、権限管理・閲覧ログ) |
| 検索 | **文字バイグラムのコサイン類似**(ブラウザ内・依存なし) | **埋め込み(ベクトル)検索**(サーバ側。例: Voyage等の埋め込みモデル+pgvector) |
| 生成 | デモ用の内蔵ジェネレータ(`callAI('shinsei')`) | Claude API(サーバ経由)。参照事例+体制データ+様式定義をプロンプトに構成 |
| 様式 | 特定事業所加算 届出一式(体制等状況一覧表・届出書・整備状況説明) | 処遇改善加算計画書、各種体制届、LIFE様式、自治体別様式へ順次拡大 |
| 制度情報 | 事例ライブラリに手動登録 | 改定時に**弊社が制度情報パック(様式定義+文例)を配信**(単位数マスタ配信と同じ運用) |

## 3. 実装した機能(かけはしノート 📑申請アシスタント)

### 3-1. 📚 事例ライブラリ(貯める)

- 過去に提出した書類の文例・自治体の手引きの要点・社内の記載ルールを、タイトル+タグ+本文で登録
- 初期データとして3件の記載例(届出理由書の文例/個別研修計画/緊急時対応方針)を同梱
- **検索のテスト**欄で、生成時と同じ類似検索をその場で試せる(検索結果に類似度%を表示)
- 実名・個人情報は入れない運用を画面に明記

### 3-1b. 📦 制度情報パック(原典リンクつき)

事業所の文例に加えて、**厚労省・WAM NET・自治体の報酬改定情報を「制度情報」として同梱**しました(ライブラリ内で黄色の「制度情報」チップ+「🔗原典を開く」リンクつき)。生成時・検索時に事例と同じ類似検索の対象になります。

### 3-2. 📄 届出書類の作成(検索して参照しながら生成)

対象: **特定事業所加算の届出一式**(第一弾)

1. 🧾請求タブの「特定事業所加算 要件チェック」に入力済みの体制情報(研修計画・会議開催・事前指示と報告・健康診断・緊急時対応方針・介護福祉士割合・重度者対応)を**自動で流し込み**
2. 様式名+各要件のキーワードで事例ライブラリを類似検索し、**上位3件を参照事例として画面に提示**(類似度%つき)
3. 体制データ+参照事例から3文書を下書き: **体制等状況一覧表(抜粋)/届出書/体制要件の整備状況説明**
4. 現在の体制で算定できる**加算区分(Ⅰ〜Ⅳ)を自動判定**して届出書に反映
5. 未整備の要件は「④ 添付書類・提出前チェック」に警告として列挙し、添付書類の目安(研修計画・議事録・健診記録・重要事項説明書)も提示
6. A4印刷対応。**生成物は必ず人が確認・修正してから提出**する前提を画面に明示

### 3-2b. 👍 採用フィードバック(生成 → 修正 → 次回の土台)

RAGの質は「何を検索させるか」で決まります。そこで、**実際に提出できる形に直した文章を、そのまま次回の材料に戻す**ループを入れました。

1. 生成された3文書は「④ 採用して次回に活かす」に**編集できる状態**で並ぶ
2. 事業所の実態に合わせて直し、「👍 採用」を押す
3. その文章が📚事例ライブラリに **`adopted`(採用回数)つき**で保存される(同じ文書を再度採用すると回数が加算され、本文は最新版で上書き)
4. 次回の検索では、採用実績のある文例のスコアが `1 + 0.12 × min(採用回数, 5)` 倍に持ち上がり、**上位に来やすくなる**
5. サーバに共有ストア(Firestore)を設定していれば、**他の事業所が採用した文例も検索対象**になる(共有ライブラリ)

サーバ側のプロンプトでは、採用実績のある文例に「**この事業所が実際に提出して通った文章。見出しの立て方・記載の粒度・語彙をできるだけ踏襲し、事業所固有の情報だけを差し替えること**」という指示を添えています。他事業所の共有事例には「良い構成は取り入れつつ、実態と異なる記載はそのまま写さない」を添えます。

つまり **モデルは学習しないまま、使うほど「その事業所の型」に寄っていく** 構成です。ファインチューニングと違い、いつでも事例を消せば元に戻せます。

### 3-2c. 文書ごとの検索(セクション別RAG)

届出は3つの文書からできており、必要な文例も文書ごとに違います。1本の検索でまとめて引くと、どれか1文書に偏った材料しか集まりません。そこで**文書ごとに別々のクエリで検索**し、それぞれ上位2件をその文書用の材料としてプロンプトに渡しています(画面の「② 参照した過去事例」も文書ごとに分けて表示)。

| 様式 | 文書 | 検索クエリの例 |
|---|---|---|
| 特定事業所加算 | ① 体制等状況一覧表 | 介護給付費算定に係る体制等状況一覧表 特定事業所加算 区分 届出 体制 |
| | ② 届出書 | 特定事業所加算 届出書 算定開始 理由書 文例 |
| | ③ 整備状況の説明 | 個別研修計画 会議 議事録 事前指示 報告 健康診断 緊急時 対応方針 |
| 処遇改善加算 | ① 計画書(基本情報) | 介護職員等処遇改善加算 計画書 基本情報 区分 対象職員 |
| | ② 職場環境等要件 | 職場環境等要件 取組 資質向上 労働環境 やりがい 生産性向上 |
| | ③ 賃金改善と周知 | 賃金改善 方法 周知 就業規則 賃金規程 キャリアパス |

### 3-2d. 💬 AI相談(同じRAGを会話で使う)

書類作成だけでなく、**日常の疑問をその場で聞ける相談窓口**として同じ検索基盤を使います(💬AI相談タブ)。

- 質問文で事例ライブラリを類似検索し、上位4件をプロンプトに渡す
- あわせて**この事業所の登録内容の集計**(利用者数と要介護度の分布・職員数・当月の実績件数・特定事業所加算の要件充足状況・算定ONの加算/減算・ライブラリ件数)を渡す。**被保険者番号などの個人情報は送らない**
- 直近8往復の会話履歴を渡すので、「じゃあその場合は?」と続けて聞ける
- 回答には**参照した事例のタイトルと原典リンク**、続けて聞ける**質問候補**を添える
- 制度の細部・様式・提出期限は保険者ごとに異なるため、断定を避け確認先を必ず添えるようシステムプロンプトで指示

「加算の要件を調べる → 届出書類を作る」が同じライブラリの上でつながるため、相談で参照された事例がそのまま書類の材料になります。

### 3-3. 既存機能との関係

このRAG構成は新しい仕組みではなく、既に実装済みの「過去を参照して作る」機能群の一般化です。

| 機能 | 参照するもの | 検索方法 |
|---|---|---|
| 📋報告の引用 | 同一利用者の過去報告 | 利用者IDで絞り込み |
| 🧬LIFEの参照・引用 | 同一利用者の過去評価 | 利用者IDで絞り込み |
| 📑申請アシスタント | **事例ライブラリ(事業所の知識・他事業所の採用文例)** | **文書ごとの類似検索(RAG)+採用実績ブースト** |
| 💬AI相談 | **事例ライブラリ+事業所の登録内容の集計** | **類似検索(RAG)+会話履歴** |

本番では3つとも同じ検索基盤(ベクトルDB)に載せ、「この利用者の過去」も「事業所の過去事例」も同じ仕組みで引けるようにします。

## 5. セキュリティ上の位置づけ

- 事例ライブラリには**実名・個人情報を入れない**(画面に明記)。届出書類は事業所の体制に関する情報が中心で、利用者個人の情報は含まない設計
- 本番でも顧客データは**学習に使わない**(APIの学習オプトアウト)。RAGはこの方針と構造的に整合する
- 参照事例を画面に提示することで、生成文の**根拠を人が検証できる**
