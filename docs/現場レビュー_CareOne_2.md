# 現場レビュー(第2回) — CareOne(訪問介護)

顧客へのお披露目を前に、**訪問介護事業所のサービス提供責任者(兼 訪問介護員)の立場**で、1日〜1年の業務の流れに沿って通しで触った結果です。

実施日: 2026-08-25 / 対象: CareOne 検証版(デモデータ投入済みの状態)
第1回レビュー(高3・中4・低3 / 全件対応済み)は [`現場レビュー_CareOne.md`](現場レビュー_CareOne.md)

## 0. 触り方

想定した事業所: 常勤サ責2名・登録ヘルパー8名・利用者35名。直行直帰が中心。

| 時間帯 | やったこと |
|---|---|
| 朝 | 📊ダッシュボードで今日の予定と申し送りを確認 |
| 日中 | 訪問 → 📋報告、🚗移動、🛒買い物・金銭記録、✍️メモ |
| 夕方 | サ責として全員分の報告を点検、ケアマネへの連絡 |
| 月初 | 🧾実績・請求で前月を締めて国保連へ |
| 随時 | 📑申請で加算の届出、🧬LIFE、💬AI相談 |

## 1. 総評

**「記録を書く」ところは、他社の介護ソフトより明確に速い。** 一度話せば3形態が出てくる体験は、実際に手書き+ケアピア入力+口頭報告の三重作業をしている事業所には強く刺さります。訪問時の注意(その家のルール)と、その場でメモ・録音も、現場の「困った」に正確に当たっています。

一方で、**訪問介護事業所が「毎月必ずやる仕事」のうち2つが、まだアプリの外にあります。**

1. **訪問介護計画書**の作成・同意・交付・モニタリング(運営基準上の必須書類)
2. **サービス提供票への実績転記とケアマネへの返送**(毎月10日前後の最大の手間)

この2つは「あると便利」ではなく、**無いと業務が回らない**種類のものです。デモでサ責が見れば5分以内に気づきます。先に「ここは次のフェーズです」と自分から言ってしまうのが得策です。

加えて、**報告の日付が必ず「今日」になる**という実装上の問題があり、これは訪問介護の働き方(直行直帰・夜にまとめて入力)と正面から衝突します。デモ前に直すことを強く勧めます。

## 2. 【最優先】デモ前に直したほうがよい ― 実害のある不具合

### A-1. 報告・移動・金銭記録の日付が必ず「今日」になる 🔴

**症状**: 📋報告には開始・終了の**時刻**欄しかなく、日付欄がありません。保存時は無条件で当日の日付が入ります(`saveReport` / `saveTrip` / `saveMoney` とも同じ)。

**なぜ致命的か**: 訪問介護は直行直帰が基本で、**その日の記録を帰宅後の夜や翌朝にまとめて入力する**のが普通です。日付をまたいだ瞬間に、

- 前日の訪問が**翌日の実績としてカウント**される
- 月末31日の訪問を翌1日に入力すると、**翌月の請求に乗る**
- 📅予定は「未報告」のまま残り続ける

**再現**: 8/31 の訪問を 9/1 に入力 → 🧾請求の8月分に出てこない。

**直し方**: 報告・移動・金銭の各画面に**日付欄(初期値=今日)**を追加する。あわせて「昨日」ボタンがあると1タップで済みます。

### A-2. 保存した報告を編集・削除できない 🔴

保存後の履歴は開いて中身を見るだけで、**修正も削除もできません**。書き間違い・利用者の選び間違い・二重保存が起きたら、⚙️設定からデータを丸ごと消すしか手がありません。

記録の訂正は現場で日常的に起きます(「あ、鈴木さんじゃなくて佐藤さんだった」)。**訂正履歴を残したうえで編集できる**のが理想ですが、まずは編集・削除ができるだけでも十分です。

### A-3. 生成した「①正式報告書」「②記録アプリ入力用」が保存されない 🟠

保存されるのは **③サ責向け要約**と入力した元テキストだけで、①②の本文は履歴に残りません。あとから見返すには「🤖再生成」でもう一度AIを通す必要があります。

実地指導で「5月20日の佐藤さんの記録を見せてください」と言われたときに出せるのは要約だけ、という状態です。3つとも保存し、履歴から**そのまま印刷・コピー**できるようにすべきです。

### A-4. 1日2回訪問の予定が、1件の報告で両方「報告済み」になる 🟠

予定の消し込み判定が「同じ利用者・同じ日付の報告があるか」だけを見ています(`planDone`)。**朝と夕方に2回訪問する利用者**(訪問介護ではごく普通)の場合、朝の報告を出した時点で夕方の予定まで「報告済み」になり、⚠️要対応から消えます。

**夕方の記録漏れが検出できません。** 報告に「どの予定に対する記録か」を持たせるか、少なくとも時刻帯で突き合わせる必要があります。

### A-5. 🛒買い物タブが横スクロールする(幅360px以下の端末) 🟡

金銭記録の「レシートを受け取り、利用者宅に保管した」のチェックボックスが折り返さず、画面幅を9px超えます。古いAndroidやiPhone SE(初代)で左右にガタつきます。iPhone SE(第2世代・375px)以上では発生しません。

## 3. 業務上足りない機能 ― 現場が「これがないと」と言う順

### B-1. 訪問介護計画書 🔴 最大の穴

**運営基準で作成・利用者への説明と同意・交付が義務**づけられた書類です。ケアプランに沿って、援助目標・具体的なサービス内容・所要時間・留意点を書き、変更のたびに作り直します。**未作成は減算・指導の対象**です。

いま CareOne にあるのは「📅予定(曜日と時刻)」だけで、計画書がありません。そだちノート側には個別支援計画があるので、**プロダクト間で不揃い**になっています。

しかもここは**AIが最も効く領域**です。過去の報告の蓄積から「実際にやっている支援」を拾って計画書の下書きを作れれば、サ責の一番重い仕事が軽くなります。📑申請アシスタントと同じRAGの仕組みがそのまま使えます。

**デモで真っ先に聞かれる項目です。** 「次に作ります」と言えるようにしておいてください。

### B-2. サービス提供票・提供票別表(ケアマネ連携) 🔴

毎月ケアマネから**サービス提供票**が来て、実績を書き込んで返す ― これが月初の最大の手間です。多くの事業所がいまだにFAXか手渡しでやっています。

CareOne は報告から実績を自動集計できているので、**提供票の実績欄を自動で埋めて印刷/PDF出力**するだけで、かなりの時短になります。国保連伝送より先に、ここを押さえたほうが刺さります。

### B-3. バイタルの記録が構造化されていない 🟠

📷スキャンには「バイタル記録」の帳票種別がありますが、読み取った体温・血圧は**報告の自由文に流し込まれるだけ**で、数値として保存されません。📋報告にもバイタル欄がありません。

実際の訪問介護記録票にはバイタル欄があり、身体介護では毎回測ります。**推移が見られない**のは記録として弱く、「体温が3日続けて37度台」といった気づきにつながりません。数値で持てば、⚠️要対応や🧬LIFEにも自動で効きます。

### B-4. ヒヤリハット・事故報告 🟠

事故発生時の**市町村への報告は運営基準上の義務**、ヒヤリハットの収集・共有は事故防止の基本です。いまは記録する場所がなく、報告の自由文に書くしかありません。

「転倒しかけた」「薬を飲み忘れていた」は現場で頻繁に起きます。**その場でメモ・録音から1タップでヒヤリハットに昇格できる**導線があると自然です。

### B-5. 苦情受付記録 🟡

苦情処理体制の整備と記録は運営基準上の義務です。実地指導で必ず見られます。

### B-6. サ責からヘルパーへの「事前指示」 🟠

**特定事業所加算の要件そのもの**です(文書等による事前指示とサービス提供後の報告)。いまは🧾請求の要件チェックに「整備済み」のチェックボックスがあるだけで、**実際の指示を出す・受ける機能がありません**。

報告はアプリで上がってくるのに、指示は別経路(LINEや紙)という状態です。ここをアプリ内で完結させれば、**加算の根拠がそのまま記録として残る**という強い訴求になります。

### B-7. 研修記録・会議記録・各種委員会の実物 🟠

いまは「実施した/最終開催日」のチェックと日付だけです。特定事業所加算の要件、身体拘束等適正化・虐待防止・感染症対策・BCPの各委員会は、**議事録や出席者の記録**が実地指導で求められます。

⚙️設定のマスタで減算をON/OFFするだけでは、「やったことにする」運用になりかねません。記録を残せば、そのまま📑申請の事例ライブラリの材料にもなります。

### B-8. 職員のログイン・権限 🔴(デモで必ず聞かれる)

現状は端末を開けば**全利用者の全情報が誰でも見える**状態です。検証版として明示されてはいますが、経営者は必ずここを聞きます。

- 誰がどの記録を作ったか(いまは自己申告のプルダウン)
- ヘルパーは自分の担当利用者だけ見える、サ責は全員見える
- 閲覧ログ

**「本番の必須項目として設計済み」と即答できる状態**にしておいてください。

### B-9. シフト・勤務体制一覧表 🟡

**従業者の勤務体制一覧表**は運営基準上の必須書類で、実地指導の定番です。常勤換算数の計算も含みます。予定機能を持っているので、拡張の筋は良いところです。

### B-10. 写真の添付 🟡

冷蔵庫の中、傷やあざ、住環境の変化 ― 訪問介護では「写真で残したい」場面があります。📷スキャンはOCR用で画像を保存しない設計なので、**記録用の写真添付とは別機能**として要ります(個人情報の扱いは要設計)。

## 4. 使い勝手 ― 実際に手が止まったところ

### C-1. 報告履歴に絞り込みがない 🟠

「さらに表示」で5件ずつ増えるだけです。3か月使えば数百件になり、**特定の利用者・特定の月の記録にたどり着けません**。利用者・期間・担当者での絞り込みが要ります(🏡利用者一覧には検索があるので、そこと同じ体験に揃えたい)。

### C-2. 「💾 履歴に保存」の押し忘れが起きる 🟠

生成された3つの報告の**下**に保存ボタンがあります。長い文章を読んでスクロールした先にあるので、コピーだけして画面を離れると**記録が残りません**。

生成した時点で下書きとして自動保存し、確認したら「確定」に変えるほうが安全です。少なくとも、未保存のまま他のタブへ移ろうとしたら確認を出すべきです。

### C-3. 移動記録が自動車のメーター前提 🟡

自転車・原付・公共交通機関で回るヘルパーが少なくありません。メーター欄が必須なので、**距離を直接入力**するモードか、交通費(実費)の記録が欲しいところです。

### C-4. オフラインで起動できない 🟠

データが端末内にあるので**入力自体は電波が弱くても動く**のが強みですが、マニフェストとService Workerがないため、**圏外だとアプリそのものが開けません**。マンションの廊下や地下、山間部で困ります。

PWA化(ホーム画面追加+オフライン起動)は実装量が小さいわりに、現場での信頼感が大きく変わります。

### C-5. 利用者の選び方がタブごとにバラバラ 🟡

報告・買い物・LIFE・移動・メモで、それぞれプルダウンから選び直します。**「いま誰の対応をしているか」がアプリ全体で共有されない**ので、同じ人の記録を複数タブに書くとき毎回選び直しになります。

「👤佐藤さん の記録中」を上部に固定し、タブを移っても引き継ぐ形にすると、体感がかなり変わります。

### C-6. チェックボックスのタップ領域が小さい 🟡

16px角です。手袋をした手や、画面を見ずに操作する場面ではラベル全体をタップ領域にしたほうが安全です(ラベルは `<label>` で囲まれているので実際は反応しますが、見た目で伝わっていません)。

## 5. よくできている ― デモで前に出すべきところ

| 機能 | なぜ刺さるか |
|---|---|
| **📋 報告3形態の同時生成** | 手書き+記録アプリ入力+口頭報告の三重作業が実在する。**ここが一番の差別化** |
| **🏠 訪問時の注意(その家のルール)** | 代替訪問・急な担当変更で本当に困る情報。他社ソフトにあまり無い |
| **✍️ その場でメモ・録音 → 報告へ送る** | 「移動中に思い出した」を拾える。実際の記憶の落ち方に合っている |
| **⚠️ 要対応ダッシュボード** | サ責の朝の確認が1画面で終わる |
| **⭐ 特定事業所加算の要件チェック** | 加算を取り逃している事業所は多い。**売上に直結するので経営者に刺さる** |
| **🔍 請求前チェック・必要情報チェック** | 返戻は「請求してから気づく」もの。入力時点で防ぐ発想が新しい |
| **📑 申請アシスタント + 👍採用ループ** | 届出書類は年に数回だが毎回ゼロから書いている。使うほど自社の型になる説明は響く |
| **💬 AI相談** | 「誰に聞けばいいかわからない」の受け皿。サ責が一人の事業所ほど価値が高い |

## 6. デモで必ず聞かれること ― 想定問答

| 質問 | 答え方 |
|---|---|
| **「訪問介護計画書は作れますか」** | 現時点では未実装。**次の開発項目**であること、過去の報告からAIが下書きを作る構想であることを先に自分から言う |
| **「ケアマネへの提供票はどうなりますか」** | 実績集計はできているので**提供票への転記は次フェーズ**。国保連伝送より優先する旨を伝える |
| **「個人情報は大丈夫ですか」** | 検証版は端末内保存・認証なしで**実名禁止**。本番は暗号化DB・職員認証・権限・閲覧ログ。AIには**学習させない**(オプトアウト)。事業所の集計情報だけを送り、被保険者番号は送らない |
| 「いま使っているソフトから乗り換えるのは大変では」 | 併用ではなくオールインワンが方針。移行期のみCSV連携を想定 |
| 「AIが間違えたら誰の責任ですか」 | **生成物は必ず人が確認してから確定・提出**する運用が前提。画面上にも明記してある |
| 「電波が悪い家でも使えますか」 | データは端末内なので入力は可能。**オフライン起動(PWA化)は対応予定**と正直に |
| 「単位数は合っていますか」 | **初期値は暫定**。⚙️設定で事業所の実値に更新できる。改定時はマスタ配信で対応する方針 |
| 「料金は」 | (要決定) |

## 7. 優先順位の提案

| 順 | 項目 | 理由 | 規模 |
|---|---|---|---|
| 1 | **A-1 日付の指定**(報告・移動・金銭) | 実害。直行直帰の働き方と衝突している | 小 |
| 2 | **A-2 報告の編集・削除** | 訂正できないのは記録システムとして成立しない | 小 |
| 3 | **A-3 3形態すべてを保存・印刷** | 実地指導で出せない | 小 |
| 4 | **A-4 予定の消し込み判定** | 記録漏れが検出できない | 小 |
| 5 | **A-5 買い物タブの折り返し** | 見た目の問題だがデモで目に付く | 極小 |
| 6 | **C-2 保存忘れの防止** | 記録が消える | 小 |
| 7 | **C-1 報告履歴の絞り込み** | 使うほど効いてくる | 小 |
| 8 | **B-1 訪問介護計画書** | 運営基準必須。**AIの効きが最も大きい** | 大 |
| 9 | **B-2 サービス提供票** | 毎月の最大の手間 | 中 |
| 10 | **B-3 バイタルの構造化** | 記録の質。LIFEにも効く | 中 |
| 11 | **B-6 事前指示** | 特定事業所加算の根拠がそのまま残る | 中 |
| 12 | **B-4 ヒヤリハット・事故報告** | 運営基準 | 中 |
| 13 | **C-4 PWA化(オフライン起動)** | 実装量が小さく信頼感が大きい | 小 |
| 14 | **B-8 認証・権限** | 本番化の必須項目 | 大 |

**1〜7 はいずれも小さい修正で、合計しても半日〜1日程度です。** お披露目の前に片づけておくと、デモ中に事故が起きません。8以降は「ロードマップとして見せる」対象です。
